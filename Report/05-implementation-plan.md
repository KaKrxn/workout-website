# 05 — Implementation Plan

## Tech stack

| Layer | Choice | Why |
|---|---|---|
| Frontend | **Next.js (App Router) + TypeScript** | SSR keeps the analytics page fast; routing maps onto the sitemap directly |
| Styling | **Tailwind CSS + shadcn/ui** | Ready-made components, and design tokens drop in as CSS variables |
| Charts | **Recharts** (lines/bars) + **hand-written SVG** (heatmap, V-taper) | The heatmap is a plain grid; a library would be more weight than it's worth |
| Backend + DB | **Supabase** (Postgres + Auth + RLS + Storage) | Auth, database, and photo storage in one place — no middle API tier to write |
| Auth | Supabase Auth — email + Google OAuth | Lowest friction at signup |
| Offline | IndexedDB (`idb`) + service worker | A home gym can have poor signal |
| Deploy | **Vercel** | Native fit for Next.js |

## Phase 1 — Logging that actually works

**Goal:** replace the paper notebook from day one.

- [ ] Set up Next.js + Tailwind + shadcn
- [ ] Declare the full token set in `globals.css` (see `03-ui-spec.md` §1)
- [ ] Set up Supabase and write the migration from `02-data-model.md`
- [ ] Write RLS policies on every table **and verify they actually block** (try a cross-user query)
- [ ] Script that converts `data/program-seed.json` → `supabase/seed.sql`
- [ ] Write `provisionUser(userId)` — seeds plans, plan_days, plan_items, equipment, and settings
      for a new account (see `02-data-model.md` §8)
- [ ] Auth: email + Google, with middleware guarding authenticated routes
- [ ] `/today` — exercise list, set checkboxes, weight/rep entry
- [ ] Support all four exercise kinds: strength / bodyweight / duration / cardio
- [ ] Generate `client_id` on the client for every logged set from the start — retrofitting
      idempotency after data exists is painful
- [ ] `/history` — session list plus detail view

**Definition of done:** a full week of program B can be logged without touching the database directly.

## Phase 2 — Schedule and program switching

**Goal:** the plan is there to follow; nothing has to be remembered.

- [ ] `/schedule` — 7-column week view
- [ ] Generate four weeks of `sessions` (`status = 'planned'`) ahead, from `plan_days`
- [ ] **Per-day A ⇄ B toggle** plus the focus-based day pairing table
- [ ] Drag to reorder days (desktop + mobile)
- [ ] Weekly goals (5 strength days / 3 cardio) with a progress ring
- [ ] Templates: switch the active plan wholesale
- [ ] `/library` — 41 exercises, filtered by the equipment the user owns

**Definition of done:** opening the app immediately shows what today is, and switching to
program A takes one tap.

---

## Phase 3 — Progressive overload ★

**Goal:** the app helps decide rather than just recording. This is what separates it from a notebook.

- [ ] `lib/progression.ts` — double progression per `03-ui-spec.md` §2.4
- [ ] Show "last time" and "today's target" on every exercise row
- [ ] "Ready to add weight" banner + acknowledge button
- [ ] Equipment-ceiling check at 25 kg → suggest harder variations
- [ ] Stall detection at ≥ 3 weeks → suggest a 10% deload
- [ ] Round every suggested weight to the 2.5 kg adjustment step
- [ ] Automatic rest timer + Wake Lock
- [ ] **Unit tests covering every edge case in §2.4** — if this logic is wrong, the user trains wrong

**Definition of done:** the user never has to open history to find out what they did last time.

---

## Phase 4 — Body composition and the analytics page ★

**Goal:** see that the physique is actually changing.

- [ ] `/body` — log weight / body fat % / five measurements
- [ ] Compute `v_taper_ratio` + the large card against the 1.618 target
- [ ] `daily_stats` table, its refresh function, and both triggers
- [ ] `lib/stats.ts` — streak, adherence, volume, muscle balance
- [ ] **G2 heatmap** (planned rest days separated from missed days)
- [ ] **G1 V-taper** + the shoulder/waist supporting rows
- [ ] G3 body fat + weight (7-day average) — two separate charts
- [ ] G4 volume, G5 days vs goal, G6 muscle balance, G7 overload, G8 cardio
- [ ] "View as table" on every chart
- [ ] The range filter drives every chart at once
- [ ] **Walk the full checklist at the end of `04-analytics-spec.md`**

**Definition of done:** one glance answers whether the last three months were consistent and
which way the physique moved.

## Stop and reassess after phase 4

By then the app answers everything it set out to: it schedules, it logs, and it shows consistency
as a chart. Phases 5–6 make it nicer to use, not usable.

## Risks worth knowing up front

| Risk | Mitigation |
|---|---|
| Progression logic is wrong → the user trains wrong | Write the unit tests before the phase 3 UI |
| Incomplete RLS → data leaks across users | Test with two real accounts from phase 1 onward |
| Analytics page degrades as data accumulates | Build `daily_stats` in phase 4; don't defer it |
| Building features that never get used | Finish phase 1, then **actually use it for two weeks** before starting phase 2 |
